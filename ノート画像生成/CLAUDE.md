# CLAUDE.md — ノート画像生成（投稿パターン3）

## これは何

**テキストを1枚の「画像」として作り込み、フリー背景に乗せる**投稿パターン（パターン3）の一式。白背景に文字を直置きするパターン1に対し、こちらはテキストを"1枚のモノ"（手書きノート・巻物・診断票・掲示物…）として作り込むことで保存・コメントを狙う。

**生成方式はHTML/CSS→PNG**（AI画像生成は日本語テキストが崩れるため不採用）。HTMLを「フォント＋SVGの手描きパーツ＋キャラ」を重ねる合成台として使う。

---

## ★最重要ルール: デザインは毎回作り直す

**このフォルダは「テンプレ集から選んで使い回す」ためのものではない。投稿を作るたびにデザインを新しく起こす。**

- 新しい投稿 = **`designs/`に新しい`.py`を1つ書き下ろす**。既存デザインのコピペ改変で済ませない
- `designs/`にあるファイルは**「過去にどんな見た目を使ったか」の記録**であって、選択メニューではない
- 作る前に`python3 generate_note.py --list`で過去のデザインを一覧し、**見た目が被らないようにする**のが唯一の使い道
- 同じ見た目が並ぶとフィードが単調になり、「またこれか」でスワイプされる。毎回別物に見えることを優先する

## ★どのデザインでも守る形: 縦長・目安は 1:1.6

**紙は縦長にする。ちょうどいいのは縦横比1:1.6前後**（幅900〜1000px）。

- 用途はスマホのリール動画への貼り付け。正方形に近い＝1行が横に長くて読みにくい、逆に1:2は縦に長すぎる
- ただし**毎回きっちり同じ比率にしなくてよい。少し前後してよいので、デザインを最優先する**
- 列組みは1列が基本。2列に並べると横が伸びて正方形に寄る。1列で右が間延びするなら、行に地色の帯を敷いて幅を持たせる
- 貼るときリール下部にはUI（キャプション・ボタン）が重なるので、**締めのCTAは画面下いっぱいに置かない**前提で余白を見込む

## ★量産に見せない: 紙の幅は毎回わずかに変わる

`generate_note.py`は生成のたびに**`.paper`の幅を±5.5%ランダムにずらす**（ルートCLAUDE.md「量産に見せない」参照）。幅が変わると行の折り返しや余白の詰まり方も変わるので、**縦横比も自然に少しズレる**。上の「1:1.6前後」に幅を持たせているのはこのため。

- 乱数の種は既定で**slug**。**同じ投稿は何度撮り直しても同じ幅**になるので、確認しながらの修正作業は壊れない
- 投稿どうしでは必ず違う幅になる
- 実行時に`紙の幅: 940px → 936px`のようにログへ出る
- `--no-jitter` … 揺らぎを止めてデザイン定義どおりの幅で出す（デザイン調整中に使う）
- `--seed <文字列>` … 幅を振り直す（今回の幅が気に入らないとき）

**デザイン側の`.paper{ width }`は「基準値」**であって、そのまま出力されるとは限らない。±5.5%動いても崩れない組み方にすること（固定pxで横並びを詰めない、`nowrap`の長い行を作らない）。

**使い回してよいのは共通インフラだけ**（デザインではない部分）:

| 使い回す | 毎回新しく作る |
|---|---|
| `generate_note.py`（ドライバ） | `designs/<新しい名前>.py`（CSS・HTML構造） |
| `render.js`（HTML→PNG） | 配色・フォントの組み合わせ・レイアウト |
| 中身JSONのキーと装飾記法 | 装飾記法をどう見せるか（`[[ ]]`が赤か黄チョークか等） |
| `fonts/`・`designs/common.py`の部品 | 紙／板／カードといったモチーフそのもの |

### 「画像生成して」と言われたらやること

ユーザーからの依頼はたいてい**「画像作って」の一言**か、**ネタだけ指定**（例:「〇〇のやり方で」）。そこから最後まで作り切り、できたものを見せて判断してもらう。

1. **このフォルダのCLAUDE.mdを読む**（＝このファイル）。ルールと過去デザインを把握する
2. **ネタを考える**。判断材料:
   - **項目に「読者が知らないこと」が何個入っているか**（→下の節）。ここが伸びを決める
   - ルートの`分析/`と過去の投稿パフォーマンスの記録（あれば）
   - 季節性・時期性（ジャンルによっては刺さる時期がある）
   - ネガ型（やめとけ）とポジ型（伸びる人がやってる）を交互に回して飽きさせない
   - `samples/`にある過去ネタと内容が被っていないか
3. **中身JSONを書く**（`samples/<slug>.json`）
4. **デザインを新規に起こす**（`designs/<新しい名前>.py`）。過去と別物に見えるモチーフを選ぶ
5. **生成 → PNGを目視確認 → 崩れていたら直す**
6. ユーザーに渡すのは`output/<slug>_paper.png`（透過）。実写背景への合成はユーザーがCanva/CapCutで手動、または`動画生成/make_note_video.py`

### 新しい投稿を作る手順（機械的な部分）

1. `python3 generate_note.py --list`で過去デザインを確認（被り防止）
2. 中身JSONを`samples/<slug>.json`に書く（キーは下記。`"design"`に新しいデザイン名を入れる）
3. `designs/<デザイン名>.py`を新規作成し、`LABEL` / `CSS` / `build_body`を書く
   - モチーフから考える（ノート／黒板／雑誌の中吊り／スマホUI／掲示板／答案用紙／チラシ…ジャンルに合うものを探す）
   - カード本体には**必ず`class="paper"`**を付ける（`render.js`がこれを探して背景透過PNGを切り出す）
   - `#stage`は外側のプレビュー背景。この2つだけが`render.js`との約束
4. `python3 generate_note.py samples/<slug>.json`
5. **出力PNGを目視確認**（崩れてもエラーにならない）

## 使い方

```bash
python3 generate_note.py samples/<slug>.json                # JSONの "design" で生成
python3 generate_note.py samples/<slug>.json --design karte # デザインだけ差し替えて試す（比較用）
python3 generate_note.py samples/<slug>.json --no-jitter    # 紙幅の揺らぎを止める（デザイン調整中）
python3 generate_note.py samples/<slug>.json --seed abc     # 紙幅を振り直す
python3 generate_note.py --list                             # designs/ の一覧（被り確認用）
```

出力（`output/`）:
- `<slug>_paper.png` … **カードだけ・背景透過**。これを実写背景に合成して本番リールにする。**通常はこの1枚だけが出る**
- `--preview`を付けたときだけ`<slug>_preview.png`（外側の`#stage`ごと撮った不透明PNG）も出る
- `--design`で上書きしたときだけ`<slug>_<デザイン名>_*.png`になる（元の出力を潰さないため）

## 中身JSONの書き方

```json
{
  "slug": "英数字の出力ファイル名",
  "design": "使うデザイン名（designs/<これ>.py。省略時は note）",
  "title": "大タイトル（例: [[アホ]]勉強法）",
  "items": ["①〜の項目を配列で。数はいくつでもOK（5でも7でも10でも）"],
  "cta_line": "CTAの1行目（例: 本気で[[やりたい]]人は）",
  "cta_follow": "強調ワード（例: フォロー）"
}
```

このキー構成は共通インフラ側なので、デザインを変えても同じJSONが使い回せる（＝中身とデザインが分離している）。**新しいデザインでキーを増やしたくなったら、そのデザインだけが読む任意キーとして足してよい**（`c.get("xxx")`で拾う）。

**インライン装飾記法**（`title` / `items` / `cta_line`で使える）:

| 書き方 | 変換先 | 意味 | 実際の見え方 |
|---|---|---|---|
| `[[ここ]]` | `<span class="em">` | 強調1（パワーワード） | デザインが決める |
| `{{ここ}}` | `<span class="kw">` | 強調2（補足キーワード） | デザインが決める |
| `__ここ__` | `<u>` | 下線・マーカー | デザインが決める |
| 改行（`\n`） | `<br>` | 意味の切れ目で行を折る | そこで必ず改行される |
| 装飾なし | — | 地の文 | — |

**新しいデザインを書くときは`.em` / `.kw` / `u`の見た目を必ず定義すること**（定義し忘れると強調が効かないまま出力される）。

## ★2行以上になる文は、自分で改行を入れる

ルートCLAUDE.mdの全パターン共通ルール。**2行以上になる文は、JSONに`\n`を入れて意味の切れ目（句点・読点・文節の頭）で自分で折る**。自動折り返しに任せてはいけない。

- 任せると**意味の切れ目でないところで割れる**（小書き文字が行頭に来るなど）
- 紙の幅は投稿ごとに±5.5%揺らぐので、**折り位置も投稿ごとに動く**。自動任せだと読みやすさが毎回ブレる
- 保険として`designs/common.py`の`BASE_CSS`が全デザインに`line-break: strict`を効かせている（`ゃゅょっー`の行頭を禁止）。ただしこれは**崩れ方をマシにするだけ**で、意味の切れ目で折ってくれるわけではない
- Tier表のような手書きHTMLは`generate_note.py`を通らないので`BASE_CSS`が効かない。`* { line-break:strict; word-break:normal; }`を自分で書く

## 文字数の目安（**デザインごとに変わる**）

崩れ方はレイアウト次第なので絶対的な上限ではない。新しいデザインを作ったら自分で確かめる。目安として、シンプルな1列組みのデザインなら:

| 項目 | 目安 | 超えるとどうなる |
|---|---|---|
| `title` | 9〜12文字/行 | `white-space:nowrap`なら折り返さず紙の左右にはみ出す |
| `cta_line` | 10〜14文字 | 2行に折り返り、1文字だけが2行目に孤立してダサくなる |
| `items` | 16〜20文字 | 2行に折り返す（崩れはしないが行揃いが乱れて読みづらい） |

装飾記法の記号自体は文字数に数えない。強調（`[[ ]]`）は太めに出るぶん少し幅を食うので、上限ギリギリなら1文字削る。

**出力したPNGは必ず目視確認すること**（崩れは実行時にエラーにならず、黙ってレイアウトが壊れる）。

## ★載せるのは4つだけ（一言欄・eyebrow・hook は原則入れない）

**カードに載せるのは「ラベル → 大きいタイトル → 大きい項目 → CTA」の4つだけ。**

- **締めの一言（`note`キー）は入れない**。項目リストの下に置く小さい文章のブロックのこと。**どのデザインでも作らない**
- `eyebrow`（上見出し）と`hook`（診断バッジ）も**外す前提で組む**（使う場合もユーザーの明示指示があるときだけ）
- **削って空いた縦幅は、タイトルと項目の拡大に回す**。カードを小さくするのではない

リールは短時間で消費される。小さい文字のまとめ文は読まれないうえ、本当に読ませたいタイトルと項目の面積を奪う。言いたいことがあるなら**項目の1つとして書く**か、キャプション側に回すこと。

`items`が8個を超えるときはこの限りではない（縦が足りなくなる）。そのときも足すのは項目であって、まとめ文ではない。

## ★項目には「読者が知らないこと」を入れる（型より中身）

**伸びを決めるのは、項目に読者の知らない情報が何個入っているか。**「手順型」（やり方を渡す）と「特徴型」（〜な人の特徴、というカテゴリ提示）という型の違いは、それを載せる器でしかない。

同じ生成パイプラインを使っても、項目の中身次第で結果は大きく分かれる（勉強系アカウントでの実測では、保存率が一桁台と二桁台で差がついた）。差が出るポイントは決まっていて:

- `title`は**カテゴリ名でなく主張**にする（「〇〇は順番ゲー」等、断定・逆説フレーミング）
- 読者が**既に自分で分かっていること**を並べても、持ち帰れる情報が0個になり伸びない
- 一方で読者が**知りようのない基準・裏側の情報**（隠された選考基準・業界の裏事情など）は、特徴を並べるだけで新情報になる

**特徴型を使ってよいのは「隠された基準」のときだけ**。それ以外のテーマは必ず手順型（やり方を渡せる）にする。ダメ出しを思いついたら「ではどうするか」に置き換える（例:「〇〇していない」→「1日〇回〇〇する」）。

JSONを書くときのチェック:

- `title`は**カテゴリ名でなく主張**（例: 「〇〇は順番ゲー」「〇〇は消す科目」）
- `hook`（使う場合）は**脅しでなく約束**（○「この順でやると急に伸びる」／×「〇個以上で伸び止まる」）
- `items`は全部「やり方」。書き終わったら**1個ずつ「これ読者は知らないか？」を確認**する

自分のジャンルで実際にどのパターンが伸びるかは、`分析/`のインサイトで検証して記録を更新すること（この節はあくまで出発点）。

## ネガ型・ポジ型

毎回ネガ型（やめとけ）だと飽きる＆ブランド的にキツい回が出るので、**ポジ版（うまくいってる人がやっていること）**も回す。デザイン側でもトーンを合わせられる（暗い板＝硬派、明るい紙＝やわらかい、赤帯＝煽り）ので、**ネタのトーンとデザインのトーンをセットで考える**。

## フォルダ / ファイルの役割

- `generate_note.py` … ドライバ（JSON読み → デザイン選択 → 紙幅の揺らぎ → HTML組み立て → render.js 呼び出し）。**デザインは入っていない**
- `designs/` … **1投稿 = 1デザインファイル**。ファイルを置けば自動認識（登録作業は不要）
  - `designs/common.py` … 全デザイン共通の部品（装飾記法の変換・`@font-face`・キャラSVG）
  - `designs/<名前>.py` … `LABEL` / `CSS` / `build_body(c)` の3つを持つ
- `render.js` … HTML→PNGレンダラ（playwright-core＋キャッシュ済chromium）。`#stage`をpreviewに、`.paper`を透過PNGに切り出す。単体でも`node render.js <html> <名前>`で使える
  - `.title`が横にはみ出していたら、収まるまで自動でフォントを縮める
  - 手でHTMLを直した場合は`node render.js draft/<slug>.html <slug>`で撮り直せる
- `samples/` … 中身JSONの置き場
- `fonts/` … 手書き系フォント5種（下記）
- `draft/` … 生成された作業用HTML
- `output/` … PNG出力（既定は`_paper.png`の1枚だけ。`--preview`で`_preview.png`も）

## サンプルとして同梱しているデザイン（被り確認用）

`python3 generate_note.py --list`でも出る。**ここから選ぶのではなく、ここに無いものを作る。**新しいジャンルで使い始めるときは、まずこの3つを見て「作りの水準」を掴んでから、モチーフだけ自分のジャンル用に作り直すのがおすすめ。

| 名前 | 見た目 |
|---|---|
| `kiban` | 基盤・回路風（AI/テクノロジー寄りのモチーフ例） |
| `rosen` | 路線図風（順序・フロー系のコンテンツに合わせたモチーフ例） |
| `karte` | 診断結果票風（白い書類＋細罫＋番号チップ＋所見欄。診断・チェックリスト系のモチーフ例） |

**未使用のデザインは置かない**（在庫があると結局そこから選んでしまい、上のルールが形骸化する）。投稿1本に対してデザイン1つを作り、使ったものだけを残していく。

## フォント（`fonts/`、google/fontsからDL・OFL）

| 用途 | フォント | family名 |
|---|---|---|
| マーカー手書き（タイトル・番号） | Yusei Magic | `Yusei` |
| 鉛筆手書き（本文・上見出し） | Zen Kurenaido | `Kurenaido` |
| 丸文字 | Yomogi | `Yomogi` |
| 極太ポップ | Dela Gothic One | `Dela` |
| 極太ポップ（予備） | Reggae One | `Reggae` |

ゴシック体が要るデザインでは、環境の**Noto Sans CJK JP / Noto Serif CJK JP**をfamily名で直接指定できる（`fonts/`には無いがインストール済みのことが多い。無ければ別途導入）。手持ちのフォントで足りない雰囲気を出したいときはgoogle/fonts（OFL）から`fonts/`に足す。

## いまの仮置き（今後の課題）

- **キャラ（困り顔・忍者）は簡易SVGの仮置き**。差し替えるなら`designs/common.py`の`DOODLE_SVG` / `NINJA_SVG`を`<img>`に置換する
- **背景合成**は`動画生成/make_note_video.py`。フェードのみ・貼り付け位置や尺も投稿ごとに振る。Canva/CapCutで手貼りしてもよい（そのときも位置をきっちり揃えない）
- **スキル化はしない方向**（固定テンプレ化は、上の「毎回デザインを作り直す」方針と正面から衝突する）。中身JSONのネタ出しだけを助ける形なら可
